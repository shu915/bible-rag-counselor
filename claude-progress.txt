## 宿題(いつやるか)
- **検索の実装のとき**

  - 可能の言い方(「眠れない」→`眠れる`、本文は`眠る`)を、元の動詞に戻す処理を試す

- 進め方: ①当たりと外れの入力の類似度を並べる ②分かれなければ、選びの AI に「合わなければ選ばない(0〜3件)」と答えさせ、補う処理を外す ③0件のときの文言を決める(仕様の「3件」を変える)

## 出力の観察(質を直すための材料。まとめて決める)

入力の中身(個人の悩み・立場)は書かない。仕組みの観察だけを残す。

- **当たり外れは、聖書がその主題を正面から語っているかで決まる**: 労苦・知ることの重さ・富などは当たる。現代の主題(AI など)や、言葉だけが似た話題は外れる
- **表面の言葉に引っ張られる**: 「女」で遊女の話(箴言 6〜7 章)、「世」でヨハネ(ヨハネの「世」は別の意味)、「夜眠れない」で夜の話。書き換えは、気持ちの奥を取り違えることもある(悲しみ・疲れを、悪への憤りと読む)
- **書き換えの出力を見た結果**: 核心(孤独など)が入ることもあるが、表面の語と、相談にない説教の角度(「戒め」)が混ざる。「原因や状況」の角度が、表面の語に引っ張られる元。書き換えが良くても、順位づけと選びで外れる例もある
  - 候補: 角度を「①気持ちの奥(欲求・孤独・疲れ)/②近い主題/③慰め」に変える。「説教・決めつけを足さない」を指示。32問+現代16問で、前後を数えてから採用(評価済みの版を、勝手に変えない)
- **必ず3件を出す設計の無理**: 合わなくても、`fillSelection` で補い、解説がこじつけで合わせ、「分かりませんが」が連発する。初期の設計(コサイン類似度が低ければ「分からない」と答える)が、いまのコードにも文書にも、ない。外れを外れと見せる作り(足切り・0〜3件・件数を絞る)が要る
  - 注意: 類似度の値は「意味の合い方」と対応しない(並行記事 0.662 < 別の詩 0.695)。点数で分かれるかは、`--debug` で確かめる
- **責めるように読める節・裁きの響き**: 箴言 7 章(遊女)・イザヤ 57:14-21(17 節)・コリント第一 2:10-16(14 節)・ガラテヤ 6:7-8・詩篇 37:9-10。出さない箇所に足す候補(確認待ち)
- **解説が、画面に出ていない節に触れる**(ヨハネ 14:31・伝道の書 2:26・詩篇 90:7-8・ヨハネ 3:18)。規則「解説は、画面に出ている節にだけ触れる」を足す候補
- **迎合**: 他人への批判や価値判断の入った相談で、3件とも片方の立場を後押しする箇所になる(選びの偏り)。案: 3件のうち1件は「視点を広げる箇所」にし、解説は両方を見せる。選びも Sonnet にして、「相談者の見方を、そのまま後押しする箇所だけを選ばない」を足す実験(解説と結論を書くのは Sonnet で、釘を刺せている。偏りは選び(Gemini)から)
- **悩みと決めつける傾向**: 悩みではなさそうな入力にも、「疲れが強いときは窓口に」と添える。軽く返す余地を持たせるか
- **定番化**: 詩篇 127 篇・伝道の書 3:10-15 が、別の相談でも出る。GENERIC_PASSAGES の候補
- **引用の範囲**: 疲れた人に出すには強い節(ガラテヤ 8 節「滅びを刈り取り」)を含む。使いたい節だけに絞れたはず
- 「お金」のような語は、「お金は危うい」の束で検索すると外れる。芯(稼ぎ方・人の評価の仕方など)に割る書き換えが要る。評価用の問いに、この種の入力(不正な稼ぎ方への違和感)を入れる

ブログの材料: 「聖書に聞く」は「聖書が語っていることに聞く」もの。検索はコミュ力の低い人のように、言葉尻と連想に反応する。それを補う真意を読む役(書き換え・選び)も、読みすぎる。
- 病気の相談(軽い症状): 聖書が正面から語るので当たる(福音書の病人の癒やしなど)。直す点: ①重さの合わない箇所(死の淵の嘆きの詩篇)を、軽い病気に出す ②罪と病を結ぶ節(詩篇 41:4 など)が、引用に出て、解説が断らない ③「起きあがって世話をした」(マタイ 8:15)は、休みたい人に逆効果 ④結論の添え書きは、窓口より「医療機関」が合う(症状が重いときは受診を)

## 公開の前に、追加で(2026-11-19)

- 窓口の名前と番号を、人が公式の情報で確認して入れる(固定画面・上限や失敗の画面・「ご利用にあたって」)。入れるまで、公開しない
- **noindex を外すタイミング**: いまは、検索エンジンに載せない(next.config.ts のヘッダーと、layout.tsx の robots)。広く公開するときに、両方を外す
- 評価: プロンプトを変えた(generate-counsel.ts)ので、PR の前に、実際の AI で確かめ、`evaluator` を呼ぶ(規則)
- フォント: src/app/fonts/ に、Shippori Mincho を削った woff2(500・600・800。3,633字。OFL)。削り直すときは、google/fonts の ofl/shipporimincho の TTF を、pyftsubset で同じ字に削る
- 昼夜の切り替え(theme-toggle.tsx)・アイコン・manifest・noindex を足した

## 将来の計画(まだやらない): RAG 抜きの別リポジトリ

- RAG 版は、学習の記録として、完成した形で保存する(`feature/quality` をマージ → タグ `rag-final` → 参照元にする)
- 新しいリポジトリ(例: bible-counselor)は、RAG 抜き。画面と体験(悩みを書く → 3つの箇所・解説・結論)は、そのまま。箇所を選ぶ部分だけ、LLM(参照を答えさせ、コードが DB の段落に直して検証する)に置き換える
- 別リポジトリにする理由: このリポジトリの main の履歴に、口語訳の XML が残っている(公開リポジトリ)。履歴なしの新しいリポジトリなら、持ち込まずに済む
- 拾う: 画面一式・安全の仕組み・生成・回数制限・API ルート・注意書き・アイコン・フォント・聖書の取得と変換の道具(XML と JSON は、取得して使い、コミットしない)。作り直す: 箇所を選ぶ部分・段落の表(ベクトルの列なし)。持っていかない: 検索・書き換え・分かち書き・埋め込み・評価の道具
- デプロイは、その新しいほうだけ(辞書・pgvector・ベクトルの投入が、要らなくなる)。窓口の名前と番号は、人の作業として残る
- 先に: RAG 版と LLM 直結を、同じ評価用の問い(32問と現代16問)で、人の目で比べる(学習の仕上げ・ブログの結論)
- 公開の前に、人が確認: 口語訳の本文を画面に出すことの可否(再配布の扱いは、未確認のまま。配布元の一覧では Public Domain。新しいリポジトリでも、本文を画面に出すのは同じ)
