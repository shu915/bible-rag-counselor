# 回数制限(実装済み。2026-11-18。Neon への適用は、デプロイのとき)

ログインがなく、誰でも使える。知らない人に使われる可能性は承知のうえで、次の3段で費用を守る。

1. **IP 単位の1日の回数制限**: 最初は5回。環境変数で変えられるようにする。使われ方を見て、5〜10回の範囲で調整する
2. **全体の1日の上限**: 例: 300回。環境変数で変える
3. **OpenRouter 側の月の上限**: キーごとに、月 $5 の上限(毎月リセット)を付けた(2026-11-18)。1 回の相談が約 $0.014〜0.03 なので、月に約 170〜350 回が天井になる。**この $5 は、本番の運用のためのもの。開発では使い切るので、開発用のキーを別にして、上限を大きくする**(2026-11-18: 評価の測定と相談の試行で、1日で $5 に達し、403 になった。開発用キーは `.env.local`、月 $15 前後が目安。本番用キーは Vercel の環境変数で、$5)。上限に達すると、キーが拒否される(402・403 など。**実際に 403 が返った**)ので、アプリは「今月の利用は終了しました」とわかる形で伝える(AI に届かなかった失敗なので、数えない)。1 日の上限(2)は、この天井に合わせて小さくする。キーに期限を付けるかは未定(期限の通知は、OpenRouter にない。付けるなら、切れる日を自分で控える)

## 数える・数えない

- AI に届かなかった失敗(接続・設定・AI のエラー)は、**数えない**
- AI が答えたあとの失敗は、**数える**(わざと失敗させて、上限なしに AI を呼ぶのを防ぐため)

## 何を記録するか

- 記録は「**IP のハッシュ・日付・回数**」だけ。IP は生で持たない
- 悩みの内容は一切入れない(ユーザーの入力と返答を保存しない方針と両立させる)

## 入口の入力制限

ユーザー入力の長さは、入口の API で制限する(500〜1,000字程度。zod の `max`)。AI への入力トークンの費用と、分かち書きの処理時間(`tokenizeQuery` の上限は 2,000 字)を守る。

## 実装(src/lib/rate-limit.ts、src/app/api/counsel/route.ts、テーブル `rate_limits`)

- **順序**: 入力の検証 → **命の危険の検出(数えず、上限でも止めない)** → 枠を取る(IP の枠と、全体の枠)→ AI の処理。上限に達した人にも、危機の固定画面は届く
- **IP の取り方**: **環境変数 `VERCEL` があるとき(Vercel)だけ**、`x-forwarded-for` の先頭(Vercel が、クライアントが付けた値を上書きする)を使う。なければ `x-real-ip`。**それ以外(ローカル・別の置き場)では、偽装できるので、信頼せず、全員を `unknown` にする**(同じ枠を共有する。きびしい側に倒す。ローカルで、IP ごとの動きを試すときは、`VERCEL=1` を付けて起動する)
- **IPv6 は /64 に丸める**: 家庭や携帯の回線は、/64 の中で、IP を自由に変えられる。丸めないと、IP ごとの枠が、実質、無制限になる。IPv4 射影(`::ffff:1.2.3.4`)は IPv4 として、ポート・ゾーン ID・角括弧は取り除く。形が正しくなければ `unknown`
- **ハッシュ**: HMAC-SHA256(IP, `RATE_LIMIT_SALT`)。本番で salt がなければ、**相談のたびに hashIp が投げて、500 で失敗する**(起動時には、気づけない。**デプロイ後の最初の確認項目**)。salt なしだと、IP の総当たりで、元に戻せるため。**salt を変えると、当日の枠が、リセットされる**
- **日付**: 日本時間(Asia/Tokyo)の1日。SQL の中で計算する。古い行は、書き込みのたびに、7日より前を消す
- **上限の既定**: 本番は IP あたり 5回・全体 100回、開発は事実上、制限なし。環境変数 `RATE_LIMIT_PER_IP_PER_DAY`・`RATE_LIMIT_GLOBAL_PER_DAY` で変える。数でない・負の値は、黙って無制限にならず、止まる
- **数える・数えない**(`OpenRouterError.kind` で区別):
  - 設定の誤り(config)・接続できない(network)・HTTP エラー(http: 402・403・429・5xx)→ AI に届いていない → **枠を戻す**
  - **1回の待ち時間の超過(timeout)・全体の締め切りの超過(deadline)→ 分からない → 数える**(届いて、AI が生成している最中でも、起きる)
  - AI が答えたが使えなかった(response: 本文が空・形が違う)・そのほかの失敗 → 数える
  - **この相談の中で、AI が1回でも答えていれば、戻さない**(書き換えと選択が成功して、最後の生成が 5xx のとき、全部戻すと、生成が不安定な間、枠を減らさずに、実費をかけて使えてしまう)。成功の数は、`AsyncLocalStorage`(`withAiCallCounter`)で、リクエストの中に持つ
  - 確認済み(2026-11-18): 生成のモデルを、存在しない名前にすると、書き換えと選択は成功、生成が失敗し、`rate_limits` の count は、戻らずに 1 のまま
- **同時に来たとき**: IP ごとの枠は、1つの SQL(上限未満なら +1)で取るので、超えない。全体の枠は、確認と取得が別なので、少しだけ超えうる(費用の本当の天井は、月 $5 のキーの上限)
- 応答: IP の上限 → 429(`rate_limit`)/ 全体の上限 → 503(`busy`)/ 月の上限(402・403)→ 503(`limit`)
- 他サイトからの送信への備え: Content-Type が JSON でなければ 415、Origin が別のサイトなら 403
- 全体の枠は、確認と取得が別なので、同時の数件だけ、超えうる。`Origin` がないリクエスト(curl など)は通す: ブラウザは POST に Origin を付けるので、他のサイトのフォームからの送信は防げる。ただし、このルートに Cookie や認証はないので、本当の脅威は CSRF ではなく、「枠の浪費」。**Origin の確認は補助で、IP ごとの枠が、本体**
