# 検索(ハイブリッド検索と分かち書き)

## 方針

- ベクトル検索(pgvector)に加えて **ハイブリッド検索**(全文/キーワード検索との併用)を実装する。学習目的なので、仕組みを理解しながら進める
- 検索側のクエリは、トークンを `OR` でつなぐ。ベクトル検索の結果とは **RRF(Reciprocal Rank Fusion)** で順位を統合する

## 日本語の全文検索(分かち書き)

- Neon の標準の全文検索は日本語を単語に区切れないため、**アプリ側で形態素解析して空白区切りにした文字列**を Postgres に渡す(`simple` 設定の `tsvector`)
- 実装: [src/lib/tokenizer.ts](../src/lib/tokenizer.ts)。`@patdx/kuromoji` 1.0.4(版固定、IPADIC)を使う
  - 比較用の `Intl.Segmenter('ja')` は、品詞と原形が取れないので使わない
  - 本家 kuromoji は 2022 年から更新がなく、採用しなかった。`lindera-wasm` は、API が版で変わるため見送った(試していない)
- **文書側(DB 投入時)と検索側(ユーザー入力時)で、必ず同じ関数を使う**
  - 文書側: `tokenize` / `tokenizeToString`(長さの上限なし。最大約 2,700 字の段落を通す)
  - 検索側: **`tokenizeQuery`**(2,000 字を超えたら、処理の前に `RangeError`)。kuromoji は、同じ文字を繰り返した入力で、処理時間とメモリが急に増える(数千字で数秒、数万字でメモリ切れ)。入口の API には、もっと短い上限(500〜1,000 字)も置く

### どのトークンを残すか

- **名詞・動詞・形容詞の「原形」**だけ残す(例: 「愛しています」→ `愛す`。辞書の原形がそうなる)。助詞・助動詞・記号は捨てる
- 意味の薄い語も捨てる: 代名詞・非自立・数・接尾の名詞、非自立・接尾の動詞、非自立の形容詞、汎用の語(する・ある・いる・なる・できる・がた・ない)。全段落(5,709)で頻度を数えて決めた
- 連続するカタカナ(2字以上)は、割らずに1つのトークンにする。口語訳のカタカナはほぼ人名・地名で、kuromoji は辞書にない固有名詞を割る(「モーセ」→「モー」+「セ」。「セ」「モー」が 800 回超出ていた)ため
- 文字も数字も含まないトークン(記号だけ。長音記号「ー」だけも)は捨てる。`to_tsquery` を壊すため
- 全角英数・半角カナは、NFKC でそろえてから処理する
- 辞書にない語(原形が `*`)は、表層形のまま残す

### 既知の限界

- 可能の言い方が、元の動詞に戻らない(「眠れない」→`眠れる`。本文は`眠る`)。相談では「眠れない」「食べられない」が多い。全文検索の信号にだけ効く(ベクトル検索は影響されない)。戻す処理は、検索を作ってから試す
- カタカナ語の動詞・形容詞(「ムカつく」→「ムカ」+「つく」)は、原形にならない。聖書の本文にほぼ無いので、放置
- 文字と記号が混ざった未知語(`foo':*` など)は、トークンに残る。**`to_tsquery` に渡すときは、トークンを個別にエスケープするか、`plainto_tsquery` 系で組み立てる**。そのためのテストを書く
- 検索側の入力は、必ず `tokenizeQuery` を通す(`tokenize` を使うと、長さの上限が効かない。API の入口では zod の `max` も置く)

### 辞書のデプロイ

辞書は約 17MB。今は `process.cwd()` 基準で探す。Vercel では、辞書をデプロイに含める設定(`outputFileTracingIncludes` など)が要るはずだが、**確かめていない**。デプロイ前に、プレビュー環境で確かめる。

## 検索の最初の実測(2026-11-18、全 5,709 段落を投入した直後。段落をそのまま、プレフィックスなしでベクトル化)

ベクトル検索だけの順位(正解は、人が決めた段落):

| 相談文 | 正解 | 順位 |
|---|---|---|
| 疲れ果てて、重荷に耐えられない | Matt.11.28-30(3節) | 1位 |
| 食べ物や着る物の心配が尽きない | Matt.6.25-34(10節) | 5位 |
| 明日のことを思い悩んでしまう | Matt.6.25-34(10節) | 37位 |
| 明日のことが心配で眠れない | Matt.6.25-34(10節) | 168位 |

- 短い段落は強いが、**長い段落は、言い方によって順位が大きく落ちる**(1つのベクトルに、いろいろな話題が平均される)。「長い段落を分割するか」「書名・章節のプレフィックスを付けるか」の比較の、出発点(ベースライン)
- 全文検索(`OR` + `ts_rank`)の上位は、的外れだった(例: 「思い悩む」の相談で、ダニエル書の段落)。`ts_rank` は語の珍しさを見ないので、単独では弱い。RRF で統合してから、効き方を見る。口語訳は「思いわずらう」で、相談は「思い悩む」と書くので、語が合わない問題もある(ベクトルが補う)
- 比べるときは、**相談文と正解の段落の対を、評価用に固定**して、各案の順位を同じ物差しで測る

### 候補から LLM に選ばせる(select。2026-11-18)

ハイブリッドで候補を20件取り(各候補の本文は、冒頭300字)、LLM(`google/gemini-4-hydrogen`、推論は最小、温度0)に、悩みに合う3件を選ばせた。**書き換えの結果は、ファイルに保存して、ハイブリッドと同じものを使った**(書き換えの揺れを除いて、選択の違いだけを比べるため。`--fresh` で、書き換え直す)。

| | 開発用 17問 | 確認用 15問 | 全体 32問 |
|---|---|---|---|
| ハイブリッド 上位3件 | 47% | 27% | 38% |
| **select(候補20件)上位3件** | **59%** | **47%** | **53%** |
| 平均逆順位(全体) | | | 0.347 → 0.467 |

- 調整に使っていない確認用でも、27% → 47%。**LLM に選ばせるのは、効く**
- 候補20件に正解が入る割合(選択の上限)は、全体で66%。select の53%は、その約8割
- 費用: 1回の選択が、入力約3,300・出力約700トークンで、約 $0.010(約1.5円)。1回の相談の総額は、書き換え($0.0034)+ 選択($0.010)+ 解説の生成(約 $0.015)で、約 $0.03(約4.5円)。月 $5 で約165回

- LLM が返した id が、候補にないときは捨てる(`parseSelection`)。実装: [src/lib/select-passages.ts](../src/lib/select-passages.ts)

### 候補を何件取るか(ハイブリッドの再現率。LLM に選ばせる場合の上限)

ハイブリッドを再実行して、上位 N 件に正解が入る割合を測った(2026-11-18):

| 上位 N 件 | 3 | 10 | 15 | 20 | 30 |
|---|---|---|---|---|---|
| 正解が入る割合 | 41% | 71% | 71% | 76% | 88% |

- 10 件から 15 件にしても増えない。20 件で 76%、30 件で 88%。件数が増えるほど、LLM に渡す文章が増えて、費用が増える(20 件で、入力が約 7,000 トークン = 約 $0.01 の見込み)
- 書き換えは毎回少し違うので、同じ方法でも、数ポイント(±5 くらい)動く。1回目は上位3件 47%・10件 65%、2回目は 41%・71%
- LLM に選ばせるなら、**LLM が選べる正解の割合は、この表(候補に入る割合)を超えない**

### 分かったこと: 言い方への弱さ(2026-11-18)

同じ意味の悩みでも、**言い方だけで順位が大きく変わる**(マタイ6章の断片の最上位。3節ずつの断片):

| 相談文の言い方 | 順位 |
|---|---|
| あすのことを思いわずらうな(口語訳の言い回しそのまま) | 4位 |
| 明日のことを思いわずらう | 26位 |
| 思い煩い | 356位 |
| 明日のことが心配で、夜も眠れない | 539位 |
| 将来が不安 | 1,214位 |
| 心配事 | 2,352位 |

- 問題は、段落の分け方より、**現代の言葉(心配・不安)と、口語訳の言葉(思いわずらう)の距離**。`text-embedding-3-small` が、この距離を埋められていない。「眠れない」を足すと、睡眠の話の箇所に引っ張られて、さらにずれる
- 全文検索(分かち書き)も、同じ語のずれで外れる(「心配」と「思いわずらう」は別の語)。ハイブリッドにしても、この問題は残る
- 試した案と、これから試す案:
  1. (試した)**相談文の書き換え**: 効いた(上の表)。実際の費用は、見込み($0.0006)より大きく、1問あたり約 $0.0035。1回の相談の総額は、書き換え + 解説の生成で、約 $0.02〜0.035(月 $5 で約 150〜250 回)
  2. (試した)**書き換えた文で、全文検索(分かち書き)も使う**: 効いた(上の表。ハイブリッドで、上位3件 47%・上位10件 65%)。全文検索のクエリは、[src/lib/fts-query.ts](../src/lib/fts-query.ts) で、文字・数字だけのトークンに絞って、引用符で囲んで組み立てる(演算子や記号で、構文を壊せない)
  3. (これから)**候補を多めに取って、LLM に選ばせる**: 上位10件に入る割合(47%)が、上位3件(35%)より高い。上位10件を候補にして、LLM が相談に合う3件を選ぶ
  4. (試した)**エンベディングのモデルを変える**: `text-embedding-3-large`(1536次元に縮める)は、書き換えなしでは少し良く、書き換えありでは差がなかった(上の表)。多言語に強い別のモデルは、未試験。変えたら全件を入れ直す。(試したコードは、本番から外した。上の「実験だけのコード」を参照)
  5. (見送り)**文書側に、現代語の説明を足す**: 各段落に、LLM で説明を作って、一緒にベクトル化する。1回きりの費用が大きい(全段落で、約 $7 見込み。月 $5 の上限を超える)
  6. (試す価値あり)書き換えの推論を `none` にして、費用を下げる(モデルが受け付けるか、確認が要る)

## 実測(分かち書き)

- 5,709 段落の分かち書きは、約 4 秒。トークンが空の段落は 0 件
- 辞書の読み込みは約 0.2 秒(1 回だけ読み込んで使い回す)
