今回の変更(git diff)を評価し、合格か要修正かを判定してください。
tsc・lint・テストは Stop hook(`.claude/hooks/stop-checks.sh`)が毎回実行し、失敗していれば差し戻される。ここでは重複して実行しない。
評価は「ビルド確認」と「コードレビュー」の2段階で行います。

## 進め方
1. `git diff` と `git status` で変更範囲を確認する(未追跡ファイルも含める)。
2. `npm run build` を実行して結果を記録する(`.next/` ができる副作用は許容する)。hooks の対象外なのでここで確認する。
3. ビルドが失敗したら、レビューより先に「高」の指摘として挙げる。
4. テストの改ざんを確認する(下の「改ざんの検出」)。
5. 今回変更されたファイルと、その呼び出し元・呼び出し先を読み、下の観点でレビューする。

## 改ざんの検出
検証が通っていても、通すためにテストや値を弱めていれば不合格にする。`git diff` の `*.test.ts`、`eslint.config.mjs`、`tsconfig.json`、`vitest.config.mts` と、設定値の差分を読み、次を探す。
- 削除されたテストやテストケース、新しく足された `it.skip` / `test.skip` / `it.todo` / `.only`、`exclude` による除外
- 期待値やアサーションが、仕様の変更ではなく実装の出力に合わせて書き換えられている(厳密な比較が `toBeDefined` や `toBeTruthy` に緩む、など)
- `// @ts-ignore`、`// @ts-expect-error`、`any`、`as unknown as`、`eslint-disable` を、理由なく足して通している
- tsconfig や ESLint のルールを緩めて通している(`strict` を外す、ルールを `off` にする、など)
- タイムアウト、上限値、許可リストなどが、理由なく緩められている
- 実装を直さず、テスト側のモックや入力だけを変えて通している
- 検証の仕組みそのものを弱めている: `.github/workflows/` から `npm test` / `bible:fetch` / lint / format:check / typecheck / build の手順が消えている、`package.json` の `test` / `lint` / `check` スクリプトが空にされている、`vitest.config.mts` の `include` が狭められている。ガードでは検出できないので、`git diff` の `.github/` と `package.json` を必ず読む
見つけたら、他の指摘より先に「高」として挙げ、元の内容(差分の該当箇所)を引用する。仕様変更が理由なら、その根拠が差分や説明にあるかを確認し、なければ指摘する。

## レビュー観点
1. 【セキュリティ・プライバシー】:ユーザーの入力(悩み・弱音・懺悔)と AI の返答を、DB・ログ・エラー報告・分析ツールに残していないか。OpenRouter へのリクエストに `data_collection: "deny"` が付いているか。API キーなど機密情報の露出(`NEXT_PUBLIC_` に秘密を入れていない、クライアントに出していない、キーを読むのが OpenRouter 用の1モジュールだけか)。SQL は必ずパラメータ化されているか(ユーザー入力や分かち書きの結果を文字列で連結していないか)。入力の検証と長さの上限
2. 【RAG・検索の正しさ】:表示する聖句が、LLM の出力ではなく `id` で DB から取った本文か。LLM が返した `id` を、検索結果の3件に含まれるかで検証しているか。文書側(DB 投入時)と検索側(ユーザー入力時)で、同じ分かち書きの関数を使っているか。エンベディングのモデルと次元(1536)が、投入時と検索時で一致しているか。ハイブリッド検索の統合(RRF など)で、0件のときや片方だけヒットしたときに壊れないか
3. 【AI 連携】:AI の返却 JSON をスキーマ(zod)で検証してから使っているか。Google のモデルが拒否する JSON スキーマのキー(`minLength` など)を使っていないか。API 失敗・タイムアウト・不正な JSON・空の返答のときに、画面が壊れないか。聖書に載っていない話題(AI・ビットコインなど)を、断ったうえで抽象化して答える指示が崩れていないか
4. 【パフォーマンス】:N+1問題、不要な再計算/再レンダリング、過剰な DB/API 呼び出し、Client Component にする必要のないものを `"use client"` にしていないか。1回の相談で LLM を何度も呼んでいないか(費用に直結する)
5. 【エッジケース・異常系】:null/undefined/空配列、空の入力、極端に長い入力、検索結果が3件に満たないとき。DB 投入スクリプトが、途中で失敗しても再実行で続きから再開でき、二重に入らないか(冪等性)
6. 【メンテナンス性】:命名の意図、関数の責務分割、型定義の厳密さ(`any` を使っていないか)。マイグレーション経由でないスキーマ変更がないか。生成物(`data/bible-paragraphs.json`)や出典データ(`data/jpn-kougo.osis.xml`)を手で編集していないか

プロジェクトの方針は `CLAUDE.md` と `AGENTS.md` に従う。特に次を確認する。
- このリポジトリの Next.js は、学習済みの知識と違う場合がある。Next.js の API の使い方を指摘するときは、先に `node_modules/next/dist/docs/` の該当ドキュメントを読んで確認する(推測で「非推奨」「誤り」と言わない)
- 環境変数ファイル(`.env*`)は読まない(PreToolUse hook でもブロックされる)

## 制約
- コードは書き換えない。指摘と修正例の提示だけを行う。
- ファイルの編集、コミット、マイグレーション(`db:migrate`)の実行、DB への書き込みはしない。
- ビルドの実行で生じるキャッシュや `.next/` などの副作用は許容する。
- 推測で指摘せず、コードを読んで確認できたものだけを挙げる。

## 判定
- **合格(LGTM)**: ビルドが通り、「高」「中」の指摘がない。
- **要修正**: ビルドの失敗、テストの改ざん、または「高」「中」の指摘が1つでもある。
- `npm run build` が環境変数の不足で失敗することがある。原因がコードではなく環境変数の不足なら、「要修正」にはせず、原因を明記して未検証として報告する。コードの型エラーやビルドエラーなら、通常どおり不合格にする。
- テストが少ない部分(画面など)は、「通った」とみなさない。検証していない範囲を未検証として明記する。

## 出力形式
最初に判定を1行で書く:`判定: 合格` または `判定: 要修正`。

続けて、次の順に書く。
1. ビルドの結果(コマンド / 結果 / 備考)。tsc・lint・テストは hook が検証済みと一言添える
2. 指摘の一覧。指摘ごとに、重要度(高/中/低)、観点(1〜6)、場所(`ファイル:行`)、理由、修正コード例を書く。
3. 未検証の項目(ビルドの環境変数不足、画面のテストなし など)

指摘が1つもなく、検証もすべて通り、未検証もない場合は「LGTM」とだけ答える。
